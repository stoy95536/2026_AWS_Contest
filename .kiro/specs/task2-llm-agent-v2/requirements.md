# Task 2 LLM Agent 系統 — Requirements

> 使用 Kiro IDE 的 Spec 工作流開發。本檔記錄需求分析階段。
> 本 v2 版對應 Task 2 的通用化重構與 Task1 串接（取代舊版 task2-llm-agent.md 的固定 16 頁設計）。

## 背景

決賽現場將提供主辦單位的「旅遊資料」（11 個 Excel + 1 個 PPT 模板），須於 30 分鐘內匯入系統並產出 PPT 簡報。原本針對信用卡範例資料設計的 Agent 必須改為通用架構。

## 使用者需求

1. **通用性**：系統不能只針對信用卡，須能處理任何金融相關業務資料（旅遊、零售、保險等）
2. **金融業為核心**：以金融業為出發點，但因金融與百工百業相連，須支援跨域情境
3. **智慧分類**：語言模型須能整理資料、判別數據類型、做出正確分類
4. **策略洞察**：產出具商業價值的洞察，而非只重述數字
5. **頁數彈性**：依使用者需求決定頁數，未指定則預設 16 頁
6. **可對接**：須符合 README.md 的介面契約，讓四位成員能完成對接

## 功能需求

### FR1 — 資料智慧分類
- 系統須能從指標名稱與主體類型，自動判別業務情境與數據類型
- 支援類型：時間序列、橫截面比較、佔比結構、雙變量關聯、風險指標

### FR2 — 動態結構規劃
- 簡報結構由資料特性驅動，非固定模板
- 章節主題依指標自動分群
- 圖表類型依數據維度自動選擇

### FR3 — 策略洞察生成
- 每項洞察包含 WIRA 四要素
- 推測內容須標注
- 只能引用計算引擎的 metric_id（防幻覺）

### FR4 — 品質審核
- 驗證 metric_id 引用是否存在
- 檢查百分比大小關係邏輯
- 檢查 YoY/MoM 是否有基期資料

### FR5 — Task1 串接
- 直接讀取 Task1 的 analysis_result.json
- 使用 Task1 已計算的 chart_data 與 metrics
- 輸出格式與成員 C（PPT）、成員 D（QA）相容

## 非功能需求

- **防幻覺**：LLM 絕不自行產生數字，所有數值來自計算引擎
- **可重現**：同一資料重跑，結構與主要結論維持一致（temperature 低）
- **容錯**：LLM 不可用時自動 fallback 到規則引擎
- **可追溯**：每個數值透過 metric_id 可回溯到原始資料

## 驗收標準

- [x] Agent 程式碼不含任何硬編碼產業內容
- [x] 輸入不同領域資料產出對應簡報（信用卡/旅遊/零售驗證通過）
- [x] LLM 輸出的所有數字都存在於計算引擎結果
- [x] 頁數可由使用者指定
- [x] 符合 README 5.1/5.2/5.3 介面契約
- [x] 與 Task1 真實輸出串接，QA PASSED
