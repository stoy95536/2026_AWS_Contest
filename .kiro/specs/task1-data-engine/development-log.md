# Task 1 開發歷程 — 被實測推翻的假設與修正紀錄

> Kiro 規格驅動開發的核心價值不在「先寫規格」，而在**規格被真實資料驗證後
> 產生的修正**。本文件記錄開發過程中每一個「原本以為對、實測發現錯」的環節。
>
> 所有數字皆為實際執行結果，非估計。

## 為什麼要記錄這些

本專案要解決的問題是「簡報數字與 Excel 不符」。這類錯誤的共同特徵是
**不會拋例外**——程式跑完、沒有紅字、數字看起來合理，但就是錯的。

以下 15 項有 11 項屬於這一類。它們之所以被抓到，是因為每一步都拿真實檔案
逐格核對，而不是「跑得動就算過」。

---

## 一、規格假設被實測推翻（4 項）

### 1.1 「資料從第 1 列開始」

**原規格**：`excel_loader.detect_header_row` 回傳「第一列全為文字」的列號。

**實測**：11 份報表的資料起始列分佈於第 3～5 列
（第 3 列 5 份、第 4 列 4 份、第 5 列 2 份）。**寫死任何一個列號都會錯 6/11**。
且原函式回傳型別是 `int`，結構上就無法表達多層表頭。

**修正**：改為動態偵測，回傳表頭列的**清單**。

### 1.2 「合併儲存格數量可推斷表頭層數」

**原設計的隱含假設**：合併儲存格多 = 表頭層數多。

**實測**：表1-3 只有 **1 個**合併儲存格，卻是 **3 層**表頭
（洲別 → 國家 → 英文名）。

**修正**：唯一可靠訊號是「數值佔比」——實測表頭列一律 **0.0**、
資料列 **0.978**，中間沒有灰色地帶，門檻取 0.5 且不敏感。

### 1.3 「發現負數即標記需人工確認」

**原規格**：TASK1.md 明文「發現負數…須標記進 `needs_manual_review`」。

**實測**：負數有兩類，性質完全不同。

| 類型 | 樣本 | 判讀 |
|---|---|---|
| 量值欄整數負數 | `O5=-547`、`M5=-10751` | 人次不可能為負 → 該標記 |
| 比率欄小數負數 | `D8=-11.759`、`C5=-2.380` | 負成長完全正常 → 不該標記 |

一律標記會讓一整票正常的負成長率被誤標，**把真正的問題淹沒**。

**修正**：依欄位語意分類。修正後表1-10 的成長率負值正確不標記，
表1-2／1-3 的人次負值正確標記 81 筆。

### 1.4 「Layer 0 樣板指紋比對」

**原規格**：對表頭做 fingerprint，命中開發期已知樣板則直接套用預定義 mapping。

**分析**：決賽當天的檔案在開發期沒見過，預建的樣板庫**命中率必然為 0**。

**修正**：改為 **runtime 動態指紋**——跑第一張表時把結構存進快取，
同批次後續結構相同的工作表直接複用。本次測試集 11 份結構全異、
快取全 miss，代價為零；決賽若有同源報表才會發揮作用。誠實記錄：
在這批資料上它沒帶來任何好處。

## 二、「不會報錯但算錯」的缺陷（11 項）

### 2.1 排除「其他」欄導致每次加總少 1.79%

**症狀**：無。加總照常完成，數字看起來合理。

**發現方式**：拿自己加總的結果與報表原有的總計欄對帳。

| 年度 | 明細加總 | 明細 + 殘差 | 官方總計 |
|---|---|---|---|
| 1964 | 94,165（−1,316） | **95,481** ✅ | 95,481 |
| 2000 | 2,520,391（−103,646） | **2,624,037** ✅ | 2,624,037 |
| 2024 | 7,717,188（−140,498） | **7,857,686** ✅ | 7,857,686 |

**根因**：把「其他 Others」「未列明 Unstated」歸類為彙總欄而排除。
但它們記的是**真實的旅客人數**，只是歸不進具名分類，本質是明細。

**修正**：`AGGREGATE_ROLES` 僅含 `subtotal` 與 `total`。

### 2.2 跨檔案同名欄位重複計算，且在比率中被抵銷

**症狀**：比率完全正常，只有絕對值是兩倍。

`來臺旅客_亞洲地區_日本` 同時存在於表1-2（按居住地）與表1-3（按國籍），
是同一批旅客的兩種統計口徑。`group_sum` 把兩份加起來：

```
系統算出 2,637,964   正確值 1,318,372   剛好兩倍
```

**最危險的地方**：比率型指標中分子分母同時加倍會互相抵銷。
第一次算出的日本占比 16.7859% 與正確的 16.7781% 只差 0.008%，
**肉眼完全看不出問題**。

**修正**：新增 `ambiguous_source` 檢查，要求以 `filter(column='file')`
指定單一來源。修正後：未指定 → `failed` 並說明原因；指定 → 1,318,372 正確。

### 2.3 `metric_id` 重複且對應不同數值

**症狀**：無。JSON 有兩筆，但按 id 查值時只會拿到其中一個。

```
metric_id: 來臺旅客_亞洲地區_日本_2025
  value = 1,483,176   ← 表1-2 按居住地
  value = 1,479,392   ← 表1-3 按國籍
```

**後果**：成員 B 引用該 id 做 KPI、成員 D 回溯血緣，兩邊可能拿到不同的值
——**正是本專案存在的理由**。

**發現方式**：比對「指標筆數」與「唯一 id 數」不一致（179 vs 177）。

**修正**：`metric_id` 加入表號前綴；`verify_consistency` 加入重複偵測，
重複且數值不同時明確報出。

### 2.4 信心公式讓整份 Catalog 廢掉

把「單位可靠度」直接當成「欄位信心」，導致 190 個欄位中有 **177 個**
只因為欄名沒寫單位就被丟進 `needs_manual_review`。

**修正**：信心 = 欄位識別基準(0.9) × 單位可靠度。單位不確定只是扣分，
不是否決——一個有明確欄名、儲存格範圍、充足樣本的欄位，
就算單位判不出來，它仍是被正確識別的欄位。

修正後：**可用欄位 26 → 193，待覆核 177 → 2**。

### 2.5 詞典把「停留夜數 1～5」併成一欄

`來臺旅客_停留夜數_1` 與 `_2` 字串只差一個字元，rapidfuzz 相似度爆表被合併，
會讓 1～5 夜的人次全部混在一起加總。

**修正**：**同一張工作表的兩個欄位，按定義就是兩個不同欄位，再像也不能合併。**

### 2.6 跨檔案關聯鍵接不起來

表1-2 的期間欄表頭最下層是 `Year`、其他檔案是 `年度 Year`，
產生「Year」與「年度」兩個不同的關聯鍵，跨檔 join 因此失效。

**修正**：期間欄是靠數值特徵認出來的，既然是結構性識別就給結構性名稱。
11 份現正確共用單一 `年度` 關聯鍵。

### 2.7 總計欄跨工作表誤配

附件四同一檔案有四張表（流通卡數／簽帳金額 × P.5／P.7）。
`find_total_field` 只比對檔名，占比計算拿到別張表的總計，
變成「簽帳金額 ÷ 流通卡數」，算出 **124.11%**。

Sanity Check 攔下了，但**若兩張表量級碰巧接近，錯誤比率會落在合理區間
而完全不被發現**。

**修正**：同時比對工作表。修正後占比落在 13.30%～17.85%。

### 2.8 三方一致性因浮點精度而失敗

177 個指標中有 **35 個** JSON 與 Excel 不符。
差異量級 1e-15（相對差 3e-16，機器精度等級）。

**根因**：Excel 只保存 15 位有效數字而 Python float 有 17 位，
`12.066050672347986` 寫入後變成 `12.06605067234799`。

對任何結論都毫無影響，但驗收標準要求三方一致，評審用 `==` 比對就會看到不符。

**修正**：新增 `serialize_value()` 作為所有輸出路徑的唯一取值入口。

### 2.9 血緣缺少檔名

`source` 輸出 `{"file": "", ...}`。成員 D 拿到「歷年觀光外匯收入!C50」
不知道該打開 11 份裡的哪一份，而多份檔案的工作表名稱相近，
**猜錯會核對到別份資料上，卻仍然「對得起來」**。

**修正**：執行引擎輸出結構化 `{file, sheet, range}`。

### 2.10 非 `.xlsx` 檔案被靜默略過

```
目錄有 3 個檔案（A.xlsx / B.xls / C.csv）
系統看到 1 個，警告：（無）
```

決賽 11 份若混了 3 份舊格式，會安靜地只算 8 份。
台灣政府開放資料很常以 `.xls` 發布。

**修正**：新增統一載入層支援 `.xls` / `.csv`；不支援的格式明確列入警告。

### 2.11 期間代碼當欄名時整張表解析失敗

附件四第 1 列是 `金融機構名稱 | 11401 | 11402 | …`，
數值佔比 **0.92** 超過門檻，表頭列被當成資料列，
導致「此表沒有表頭」→ **整份檔案產出 0 筆記錄且不拋任何例外**。

這正是本專案批評舊架構的失敗模式，發生在新架構自己身上。

**修正**：辨識民國年月（`11401`）與西元年月（`202401`）代碼，
`_find_data_start` 據此排除期間代碼表頭列。

## 三、驗證方法

### 3.1 逐格回原檔核對

不接受「跑得動」作為通過標準。每個里程碑都隨機抽樣指標，
用血緣裡的 A1 座標回原始 Excel 讀該格，比對是否相符。

```
來臺旅客_飛機_松山_2025      503,940 = 歷年來臺旅客-按搭乘交通!I68  ✅
來臺旅客_華僑_2022            65,060 = 歷年來臺旅客-按國籍!AS63     ✅
來臺旅客_亞洲地區_大陸_2025   637,060 = 歷年來臺旅客-按居住地!D74   ✅
2024 明細加總              7,857,686 = 表1-3 總計欄 AT65           ✅
```

### 3.2 兩條獨立路徑交叉驗證

手寫配方從表1-3 算出的總計，與 LLM 規劃的配方算出的總計，
兩條完全不同的路徑得到同一個數字 `7,857,686`。

### 3.3 兩個領域交叉驗證

同一套程式碼零修改跑信用卡與旅遊資料。這條驗收標準原本未驗證，
一測就發現 0 筆記錄（見 2.11），修正後才真正成立。

### 3.4 單元測試釘死邊界條件

91 個測試，重點放在**邊界條件**而非「正常情況能不能跑」：
分母 0、缺基期、NaN、明細與彙總混算、跨檔重複計算、
LLM 捏造欄位、格式不支援。

## 四、外部條件與環境問題

### 4.1 AWS 憑證格式

AWS 主控台提供的 PowerShell 格式無法直接貼進 `.env`：

```
$Env:AWS_ACCESS_KEY_ID = "..."     ← PowerShell 語法
AWS_ACCESS_KEY_ID=...              ← .env 需要的
```

python-dotenv 會把整串 `$Env:AWS_ACCESS_KEY_ID` 當成鍵名，
boto3 因此找不到憑證。**決賽當天換發憑證時務必去掉 `$Env:` 前綴。**

### 4.2 憑證備份檔的洩漏風險

`.gitignore` 原本只有 `.env`，該樣式精確匹配檔名，
不涵蓋 `.env.bak`、`.env.local` 這類衍生檔。憑證輪替時很容易留下備份而不自知。
已補上 `.env.*` 並以 `!.env.example` 排除範本。

### 4.3 Windows 主控台編碼

`demo_run.py:75` 的 `print("✓ ...")` 在 cp950 主控台會拋
`UnicodeEncodeError` 並中斷腳本。`run_task1.py` 已在開頭統一切成 UTF-8，
避免在評審面前因為一個符號就整個腳本崩潰。

### 4.4 `.pyc` 進入版控

19 個 `__pycache__/*.pyc` 在 `.gitignore` 建立之前就被 commit，
已追蹤的檔案不受 `.gitignore` 約束，導致任何人執行程式後都會產生
二進位檔修改。`origin/main` 已有 commit `618c1d6 merge: resolve pyc conflict`
為證。已解除追蹤，硬碟檔案保留。

## 五、目前仍存在的限制

1. **月度資料併入年度**：轉置版面的 12 個月全歸同一年度。
   對流量型指標（簽帳金額）正確，對存量型指標（流通卡數）需由 LLM 的
   假設聲明處理。系統會留下明確警告，不靜默假裝支援。
2. **Layer 2 Embedding 未實作**：規格標示為可選項。
3. **Top-N 需兩階段**：LLM 無法在計算前知道排名。實測問「前三大客源國」時
   它會多算候選（6 個）而非嚴格前 3，屬合理迴避但非精確回答。
4. **`.ods` / `.xlsb` 不支援**：明確警告，不靜默略過。
